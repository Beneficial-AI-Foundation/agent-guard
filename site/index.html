AgentGuard · research prototype · GitHub MCP

A proved guard for what AI agents are allowed to do.

AgentGuard sits between an AI agent and its tools, starting with GitHub. You decide which actions are allowed, which need a person, and which are never allowed. A decision with machine-checked proofs enforces those rules on every action, however the agent was tricked.

01 — The idea

Agents act on real systems. Anything they read can steer them.

A coding agent with GitHub access reads issues, comments and files written by anyone, and it can push, open pull requests and merge. One crafted issue, or one eager step, is enough to cause real damage.

The problem

Instructions are not enforcement

"Never merge" in a prompt is a suggestion. A reworded request or a hidden instruction in an issue can override it, and the agent cannot tell.

The approach

A gate in front of the tools

Every action the agent takes passes through AgentGuard. Your rules decide whether it runs, waits for a person, or is refused, whatever the agent was told.

What makes it different

The gate is proved, not just tested

Tests check examples. A proof covers every possible sequence of actions, so the rules hold in cases nobody thought to test.

Prompt rules and AI reviewersSome phrasings

They judge wording, so a reworded attack can slip through.

AgentGuardEvery action

The same check on every call, whatever the wording. Proved, not sampled.

03 — How it works

One gate between the agent and GitHub

The agent talks to AgentGuard as if it were GitHub's MCP server. Every action stops at the gate, gets a verdict, and only then reaches GitHub.

01

Connect

AgentGuard uses the same MCP configuration as VS Code, with a GitHub token only it holds. The agent points at AgentGuard instead of GitHub.

02

Match

Each action is checked against your rules, including details like the branch, the file path and the repository.

03

Decide

The session's history counts too: after reading a private repo or an outsider's issue, riskier actions are held back.

04

Record

Every verdict appears live in the console and in the audit log, with the rule and the theorem behind it.

Three possible verdicts

Allow

It runs

Normal work goes straight through: reading code, creating a branch, pushing to it, opening a pull request.

Ask a person

It waits for you

The action pauses in the console with the reason and what came before it. You approve or reject; no answer means reject.

Deny

It never runs

The agent gets a clear message saying why, so it can take another route, such as asking a maintainer to merge.

04 — The proof

What is proved, in plain words

The decision is written in Lean 4, a language whose proofs are checked by a small, trusted kernel. The proofs cover the whole decision: matching the rules you wrote, and the verdict. The rest of AgentGuard only passes messages along and is kept deliberately small.

Code matches the spec

An action whose rule says deny (push to main, approve, merge) never runs.

No laundering

What the session has read is never forgotten, so summarizing or rewording private code does not make it public.

After the agent reads an outsider's issue or comment, a high-impact action never runs without a person.

Why you can trust the proofs

  • Lean's kernel checks every step of every proof.
  • The build fails if any proof is missing or relies on an unusual assumption.
  • CI checks every proof on every push and pull request.
  • A second, independent implementation is compared against Lean on 10,000 random cases.
  • Each audit log entry records which proved build made the decision.
  • Anyone can re-check the proofs on their own machine with one command.

All ten guarantees are machine-checked theorems in Lean 4: no missing proofs, no native_decide, standard axioms only. The figures are measured on the current build.

05 — Get started

From clone to a guarded agent

Everything AgentGuard needs lives in one folder per connection: the MCP configuration, your rules, and the token.

Build AgentGuard

Clone the repository and build the proved decision engine. It needs Python's uv and Lean's installer, elan; the build checks every proof.

make proofs

Add a GitHub token

Create a GitHub profile, then put a fine-grained token, limited to the repositories the agent may touch, in its .env file. Only AgentGuard holds the token; the agent never sees it.

agentguard init

Connect your agent

AgentGuard adds itself to VS Code, Cursor or Claude Code and turns off the agent's direct GitHub connection. The doctor check confirms nothing can go around the gate.

agentguard connect vscode · agentguard doctor

Adjust the rules

Start from the default rules above. Change any action to allow, ask or deny, and mark which repositories are private. A broken rules file is never loaded.

agentguard try shows the verdict for every GitHub action

Watch and approve

Open the console to see each decision live and answer approval requests. Start in audit mode to see what would be blocked, then switch to enforce.

agentguard serve · console at localhost:7070

Common questions

Does it slow the agent down?

No noticeably. A decision takes well under a millisecond; the agent's own thinking takes seconds.

What happens if something goes wrong inside AgentGuard?

It fails closed. If the decision engine does not answer or returns an error, the action is denied.

What happens to an "ask" when nobody is around?

It waits for a set time, then counts as rejected. The agent is told the action was not approved.

Can I use it with servers other than GitHub?

The gate itself knows nothing about GitHub; GitHub is one ready-made profile. Other MCP servers are connected the same way, with their own rules. The proof of concept ships GitHub only.

Does AgentGuard read or store my code?

It sees each action as it passes through, and the audit log records what was decided. Secret-looking values, such as tokens and passwords, are replaced by fingerprints.

Can my team share rules?

Yes. Rules can live in the repository and be reviewed through pull requests like any other change, with a check that rejects broken rules.

06 — Limits

What it does not do

Only what passes throughAn agent with its own terminal, git or GitHub CLI login can go around the gate. The doctor check looks for this; real deployments also need network isolation.
Rules are trustedThe rules are enforced exactly as written. If a private repo is not marked private, the decision is made on the wrong facts.
Session-level memoryAgentGuard cannot see inside the model, so anything read counts for every later action. Safe, but it may hold back some harmless actions.
What is trusted, not provedLean's checker and compiler, the code that passes messages along, the MCP libraries, and GitHub itself.
CredentialsAgentGuard uses a token you create and put in its .env file. It has no sign-in flow of its own, so you rotate the token yourself.
Research prototypeNot a security product and not externally reviewed.
